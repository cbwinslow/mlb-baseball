# Roadmap

Only Phase 1 is broken into concrete steps right now — Phases 2 and 3 get planned when Phase 1 is actually done (see [NORTH_STAR.md](NORTH_STAR.md)).

## Phase 1 — Data ingestion pipeline

Rough build order, each step re-runnable and tested before moving to the next:

1. ✅ **Project scaffolding** — repo layout, `.env.example`, dependency management, DB connection helper, migration tooling for the raw/core/gold schemas.
2. ✅ **Chadwick Bureau Register connector** — the ID crosswalk. Built first because every other source gets joined against it.
3. ✅ **Lahman connector** — season-level historical stats. Current data requires a manual download (see `docs/DATA_SOURCES.md`); network fallback frozen at 2021.
4. ✅ **Retrosheet connectors** (eight — see `docs/DATA_SOURCES.md`) — pre-parsed CSV product (`retrosheet`, ADR-004); raw play-by-play event files via `cwevent`/`cwgame`, 1910–2025 plus post-season/all-star/Negro League (`retrosheet_event`, ADR-009/ADR-010); box-score-only games via `cwbox` for everything raw event files don't cover — 1871/1872/1874 NA seasons, 1898–1909, and additional Negro League games (`retrosheet_box`, ADR-012); classic game logs back to 1871 plus postseason logs (`retrosheet_gamelog`); ballpark/team/biographical reference data (`retrosheet_reference`); annual rosters (`retrosheet_roster`); planned schedules (`retrosheet_schedule`); the (frozen) transaction database (`retrosheet_transaction`). Reconciled against the CSV product end to end: 98.3% of all games have raw-file coverage; the remainder is a genuine gap in what Retrosheet has published as a standalone download, not a parsing limitation — see ADR-012.
5. ✅ **Reusable ingestion infrastructure** — disk-persisted downloads with a per-source JSON manifest so a bootstrap is resumable without re-fetching (`mlb_baseball/manifest.py`, ADR-008); `mlb doctor` hardened to report cleanly (not crash) on a database that's never been migrated, plus checks for the `downloads/` directory and the Chadwick CLI tools (ADR-011); `mlb_baseball/load.py`'s loader now tolerates a later batch having columns an earlier one didn't, rather than failing on COPY.
6. ✅ **MLB Stats API connector** (`mlb_api`, ADR-015/016/017/018/019/020/025) — full-history schedule (1901–present), standings (1969–present), rosters (1901–present), transactions (2000–present, fills the real gap left by `retrosheet_transaction`'s Nov 2021 freeze), venues (~1,667, full catalog), team configuration history, player bios, and amateur draft picks (1965–present); play-by-play/box-scores/umpire-assignments from 2026 on (exactly where Retrosheet's own most recent published season stops, verified play-for-play equivalent on a real shared game first); win-probability/linescore/game-context from **1950 on** — a much wider range, since it has no Retrosheet equivalent at all (ADR-019); append-only live-game-state capture (`raw.mlb_live_game`). Extended (ADR-020) with the full reference/personnel/organizational surface: sports/leagues/divisions/seasons, player pool, free agents, coaches, alumni, personnel, affiliates, attendance, game pace, official per-player/per-team season stats and category leaders, awards catalog, conferences, official scorer/umpire/datacaster directories — every one of the API's 64 endpoints is now built, confirmed broken, or explicitly excluded with evidence. Scheduled via cron every 5 minutes (`scripts/mlb_api_update.sh`, ADR-016) for live/schedule/standings freshness; the ADR-020 reference/personnel data deliberately isn't on that cron (refreshed only via an occasional manual `bootstrap()` re-run — re-running it every 5 minutes would be pure API load with no freshness benefit). `net.call_with_retry` no longer wastes the full retry budget on a confirmed 404 (ADR-025) — found while running the full historical backfill, a real fix, not speculative.
7. ✅ **Statcast connector** (`statcast`, ADR-017) — pitch-level tracking data via `pybaseball.statcast()`, full history from 2008 (PITCHf/x era; full Statcast fidelity from 2015). Confirmed a strict superset of MLB API's own pitch data (119 columns vs. ~20), so all pitch-level tracking lives here exclusively. Weekly date-range batching, ~2.6s/day confirmed. Full 2008–present history bootstrapped against production (13.4M+ rows), zero known gaps.
8. ✅ **Core layer** — dimensions and facts built on top of the raw tables, joined via the Chadwick crosswalk (`mlb_baseball/conform.py`, `mlb conform`, ADR-013). `core.player`/`core.team`/`core.game` (dimensions, real PK/FK/indices) and `core.play`/`core.pitch` (facts, unifying Retrosheet+MLB API plays and Statcast pitches respectively) all built and verified against production. Extended (ADR-028) with `core.market` (Polymarket/Kalshi market-implied probability, matched to `core.game` — this project's own stated differentiator per `NORTH_STAR.md`, previously inert in `raw`), `core.player_war` (Baseball-Reference's own WAR), and win-probability columns on `core.play`. Also fixed a real, separate bug found doing this: `core.team.last_year` was silently NULLing every team match for 2022+ games. Further extended (ADR-029) with `core.team.mlb_team_id` — team identity resolved by MLB's own stable numeric ID, the team equivalent of `core.player.mlbam_id`, self-bootstrapped by majority vote rather than more string matching — plus a small `core.team_alias` table for Polymarket/Kalshi, the one case with no shared numeric ID at all. Fixed the Athletics' 2025 relocation breaking `core.game` team resolution (MLB's schedule data now lists them as bare `"Athletics"`, no city) as part of the same change.
8b. ✅ **Statcast leaderboards + Baseball-Reference connectors** (`statcast_leaderboard`, `bref`, ADR-018/024) — all 18 Savant leaderboards: the original 8 tracking-only ones not derivable from pitch-level data (sprint speed, catcher pop time/framing, outfielder jump/catch-probability/directional-OAA, outs-above-average, baserunning splits), plus 10 official-aggregate leaderboards added per ADR-020's "ingest everything" direction (batter/pitcher exit-velo-barrels, expected stats, percentile ranks, pitch arsenal, arsenal stats, spin-direction comparison). Baseball-Reference season batting/pitching stats plus Baseball-Reference's own WAR calculation (`bwar_bat`/`bwar_pitch`, full history 1871–2026, ADR-024) — not available from Lahman or MLB Stats API. FanGraphs itself confirmed blocked (Cloudflare 403) — not built; see `docs/DATA_SOURCES.md` Deferred section. `pybaseball`'s full exported namespace was checked function-by-function against what's used (ADR-024) — everything not built is either redundant with data already pulled, a confirmed library bug, or genuinely impractical (no bulk form), each with direct evidence, not a guess.
8c. ✅ **Unified bootstrap/update** — `mlb bootstrap`/`mlb update` run every registered connector in one command, iterating `registry.CONNECTORS` (the same list `mlb doctor` uses), logging and continuing past any single connector's failure. Extended with a second, daily cron cadence (`scripts/mlb_daily_update.sh`, ADR-023) covering every connector's `update()`, not just `mlb_api`'s.
8d. ✅ **Retrosheet completeness pass** (`retrosheet_box`, ADR-021) — `cwbox`'s 7 supplementary per-event lists (doubles/triples/homeruns/stolen bases/double plays/triple plays/sac bunts), previously unparsed. "Retrosheet discrepancy files," referenced as a build target from outside this project, confirmed not to exist as an actual Retrosheet product — the closest real match ("Official Daily Totals") turned out to be scanned PDF ledgers, outside this pipeline's technical shape.
8e. ✅ **Pipeline reliability** (ADR-022/023) — stale `meta.ingestion_run` rows (from an externally-killed process) now self-reap via PID liveness checking, run automatically by `mlb doctor`. Bootstrap procedure documented (`docs/ARCHITECTURE.md` "Bootstrap procedure", README "Setup").
9. ✅ **Polymarket connector** (`polymarket`, ADR-026) — MLB daily-game and season-futures market-implied probabilities via the public Gamma API, no auth needed. `outcomes`/`outcomePrices`/`clobTokenIds` exploded into a normalized outcome table.
10. ✅ **Kalshi connector** (`kalshi`, ADR-027) — 155 confirmed-MLB series (games, spreads/totals, player props, season leaders, every major award AL/NL, division/league/World Series champions, draft, coaching changes, Home Run Derby, All-Star props). No authentication needed for reads despite the account-signup requirement and documented RSA-PSS request-signing scheme — confirmed directly, that's for trading actions, not public market data.
11. ✅ **Market price-timeseries capture** (ADR-049, reverses ADR-026's original exclusion) — the owner reversed course: full intraday line-movement history is now in scope, for an oddstrader-style product. `polymarket.backfill_history()`/`kalshi.backfill_history()` land historical per-token prices (`raw.polymarket_price`, CLOB `/prices-history`, ~126K MLB daily-game tokens) and candlesticks (`raw.kalshi_candle`, `KXMLBGAME` only, Kalshi's own candlesticks endpoint) as owner-triggered one-off backfills (`mlb ingest <source> --mode backfill`) — not run by `bootstrap()`/`update()`. Both connectors' `bootstrap()`/`update()` now also append a current-price snapshot for still-open/active markets into `raw.polymarket_snapshot`/`raw.kalshi_snapshot` every run, at no extra API cost.

Phase 1's core ingestion pipeline (steps 2–10) is done: every connector runs cleanly end-to-end, is idempotent, has tests, and (where it has a natural join target) lands in the core layer. Every source's full surface has been explicitly audited against what it actually offers (not assumed complete) — see `docs/DATA_SOURCES.md` and the ADR log in `docs/DECISIONS.md` for the evidence behind every inclusion and exclusion. Nothing left in Phase 1.

## Phase 2 — ML modeling workflows

Kicked off (ADR-032). First target: game win/loss probability. Techniques and sources: [docs/RESEARCH.md](RESEARCH.md); every model decision logged as an ADR (ADR-032/033) same as everything else in this project.

**Built and running against production, end to end:**
- `gold.game_feature` (migrations 0012-0015) — point-in-time win%/last-10 win%/run-diff/Pythagenpat/Elo, one row per game. Sources upcoming games directly from `raw.mlb_schedule` (`core.game` only ever holds completed games by design), identity is `mlb_game_pk` (works before and after a game lands in `core.game`), degrades gracefully if `raw.mlb_schedule` doesn't exist yet.
- Three models in `mlb_baseball/model/`, all writing to `gold.prediction`: **log5** (689 predictions), **Elo** (793 predictions, sequential Python rating walk — not SQL window functions, which don't fit a cross-team-dependent state machine), and **gbm-v1** (XGBoost, ADR-033) — trained on 209K historical games, validated on 4,666 (2024-2025): log-loss 0.6795 vs Elo's 0.6797 (essentially tied) and log5's 0.9295 (log5's season-to-date win% is noisy early in a season and gets punished hard by log-loss — a real limitation of the simplest baseline, not a bug).
- `mlb predict` (daily cron, alongside `mlb conform` — neither was scheduled before this session) generates predictions; `mlb train` (separate, deliberate command, not part of the daily cron) retrains gbm-v1 and only overwrites the saved model if it beats both baselines.

**Honest reading of the gbm-v1 numbers:** barely beating Elo despite having 10 features to Elo's 2 means the current feature set doesn't carry much more signal than Elo's rating already captures. Acted on directly — three more features built and verified against real production data since:

- **Rest days** — trivial, closes a reserved schema gap.
- **Starting-pitcher quality** (true FIP + K%/BB%/HR%, ADR-034) — reconstructed from `raw.retrosheet_event`'s per-play data (season aggregates like `bref_pitching` would leak future starts mid-season, same trap ADR-032 flagged for WAR). Verified against real 2018 deGrom data, then at full scale (13,613 pitcher-seasons) against `raw.bref_pitching`: 98.3% match — matching this project's own already-documented Retrosheet coverage rate almost exactly. Wired as a permanent `mlb doctor` reconciliation, not a one-off check.
- **Park factor** (`mlb_baseball/model/park.py`, ADR-035) — trailing 3-year window, purely derived from `core.game`'s own scores, zero leakage risk by construction, zero external dependency. Verified: Coors Field correctly ranks highest (135.4) in real 2024 data, matching sabermetric consensus.
- **Team wOBA** (`mlb_baseball/model/offense.py`, ADR-036) — FanGraphs' published formula, recreated (not scraped — they explicitly don't support scraping/API access at all). Verified: real 2023 league-average wOBA computed at .317, matching the known value; real 2024 team values all land in the correct .295-.333 range.
- **wRC+** (`mlb_baseball/model/offense.py::compute_wrc_plus`, ADR-037) — park- and league-adjusted extension of team wOBA, built on top of the two features above. Sanity-checked algebraically (league-average hitter in a neutral park must reduce to exactly 100 by definition — a real regression test) and verified: real 2024 values all land in 86.9-103.6, clustered around 100.
- **Prior-season team WAR** (`mlb_baseball/model/war.py`, ADR-038) — closes the last ADR-032-reserved `gold.game_feature` column (`home_war_prior`/`away_war_prior`). Lagged one full season by construction (zero leakage risk), sourced from `core.player_war`. Surfaced a real team-identity crosswalk gap: `core.player_war.team_code` uses Baseball-Reference's own abbreviations, genuinely different from `core.team.retro_team_id`'s Retrosheet codes — fixed with a dedicated `_BREF_TO_RETRO` mapping. Verified: 2023's Braves (55.1 WAR) and Rangers (47.8) — both real, well-known strong teams — correctly rank highest entering 2024.
- **Bullpen quality and fatigue** (`mlb_baseball/model/bullpen.py`, ADR-039) — team-level relief FIP/K%/BB% plus a trailing-3-day fatigue signal, both point-in-time and no-leakage. Deliberately team-level, not pitcher-level: which reliever pitches today is an in-game decision, so per-pitcher composition would leak the target. Caught a real design bug before it touched production data: without a full team-game backbone (every team × every game, zero-filled), both signals would silently go NULL for a game where a team happened to use zero relievers, regardless of real prior workload.
- **Prior-season defensive value via Statcast OAA** (`mlb_baseball/model/oaa.py`, ADR-040) — closes the FanGraphs UZR/DRS gap for good (confirmed permanently blocked, HTTP 403 on every scrape attempt) using `raw.statcast_oaa.fielding_runs_prevented`, already ingested but unused until now. Same prior-season lag as WAR. Found two real data-shape quirks against production before building: OAA rows are per player-season-*position* (must sum, not dedupe) and Statcast's own team-name spelling mismatches `core.team.nickname` in exactly three cases (D-backs/Rays/Guardians).
- **Prior-season team baserunning speed** (`mlb_baseball/model/speed.py`, ADR-041) — `competitive_runs`-weighted `raw.statcast_sprint_speed`, lagged one season. Not redundant with anything already built — no other feature captures raw speed. Explicitly ruled out team-level Statcast xwOBA/barrel%/hard-hit% first: checked the schemas directly, found no team column on either source table, and it would have duplicated team wOBA's already-better within-season coverage anyway.
- **Prior-season catcher framing** (`mlb_baseball/model/framing.py`, ADR-045) — a real, distinct signal (called-strike rate, not something FIP already prices in), team identity resolved by reusing war.py's own bref/Retrosheet crosswalk through `core.player_war` rather than a new one. Verified against real 2024 data; found and understood a real ~48% coverage gap traced to `core.player_war`'s own minimum-playing-time threshold, not a bug.

**gbm-v1 has been retrained** against every one of the columns above (ADR-044, `FEATURE_COLUMNS` 10 → 37) — XGBoost's native missing-value handling (not a strict non-null filter, which would have gutted the training set and zeroed out live 2026 predictions entirely) lets a row missing some optional features still train/predict on whatever signal it has. Real result on real data: log-loss 0.6793 vs Elo's 0.6797 and log5's 0.9295 — a genuine but modest gain over the original 10-feature model's 0.6795, limited by how many of the new columns are `NULL` for older/current-season rows, not by the features lacking signal. **A live production bug was caught and fixed the same session**: adding catcher framing to `FEATURE_COLUMNS` without a successful retrain broke `mlb predict` outright (`ValueError: Feature shape mismatch, expected: 37, got 39` — the saved model on disk still expected the old shape); reverted immediately, verified `mlb predict` runs clean again, and saved a standing lesson to always confirm a retrain actually saves before leaving a `FEATURE_COLUMNS` change in place.

**Known gap, shared by starter quality, wOBA, wRC+, bullpen, and framing — now fully closed for starter/offense/bullpen**: `raw.retrosheet_event` covers 1910-2025 only, so all of these were `NULL` for the live 2026 season `mlb predict` actually serves. Starter quality's and team wOBA/wRC+'s 2026 equivalents are now built (`mlb_baseball/model/starter.py::compute_live`, `mlb_baseball/model/offense.py::compute_live`/`compute_wrc_plus_live`, ADR-046), sourced from `raw.mlb_playbyplay` (a genuinely different schema — descriptive event text, no starter-flag field, a running per-half-inning outs counter instead of an outs-per-play field) and verified against a real, identifiable 2026 pitcher (27 real starts, per-play out counts hand-checked). `compute_live()` itself only ever backfills *completed* 2026 games — forward-looking prediction for a game that hasn't been played yet needed a probable-pitcher data source, which didn't exist at the time. **That gap is now closed** (ADR-048): `raw.mlb_probable` (person_ids via `schedule`'s own `hydrate=probablePitcher`, append-only snapshots so a scratch is visible, not silently overwritten) plus `mlb_baseball/model/starter.py::compute_probable` populate the same starter columns for `gold.game_feature` rows where `home_win IS NULL`, resolved via `core.player.mlbam_id` and dated through `raw.mlb_schedule` rather than `core.game` (no dependency on `conform()` having run yet). **Bullpen's own version is now closed too** (ADR-051): `mlb_baseball/model/bullpen.py::compute_live`/`compute_upcoming` — `compute_live` mirrors `compute_live`/`compute_wrc_plus_live`'s completed-2026-game treatment (same `raw.mlb_playbyplay` source), and `compute_upcoming` needed genuinely different, simpler wiring than starter's `compute_probable` rather than a reuse of it: bullpen quality/fatigue is team-level by design, so it never depends on `raw.mlb_probable`/`core.player` at all — team identity comes straight from `gold.game_feature.home_team_id`/`away_team_id`, already resolved by `features.py` for every upcoming row.

**Forward-test against real 2026 outcomes, corrected to game grain** (2026-08-05, ADR-055): the earlier table counted every stored prediction snapshot as an independent observation (`n=352/453/430`). That was wrong: rerunning a model more often increased its apparent sample size. `mlb evaluate` now selects exactly one eligible pre-game prediction per game at a named cutoff and restricts every model to the exact same games. The production tie-out below uses the `close` cutoff and the 47 games shared by all three historical model versions; intervals are a deterministic 200-sample game-grain bootstrap.

| model | n | log-loss | Brier | accuracy |
|---|---|---|---|---|
| `gbm-v1` | 47 | **0.6764** | **0.2417** | **0.5745** |
| `elo-v1` | 47 | 0.6974 | 0.2521 | 0.4894 |
| `log5-v1` | 47 | 0.6928 | 0.2500 | 0.4894 |

The corrected sample is directionally encouraging for `gbm-v1`, but 47 shared games is far too small to claim that it genuinely beats the baselines. `log5-v1` is also retained here only to reproduce the historical comparison; ADR-054 established that its formula is invalid. A trustworthy post-fix comparison requires accumulating `log5-v2` predictions and evaluating all challengers at the same named cutoff. Coverage is reported separately by the command (`gbm-v1=47`, `elo-v1=53`, `log5-v1=47` before matched-sample restriction) so missingness is visible rather than silently changing the leaderboard population.

**`core.market`'s pre-game-snapshot gap is now closed** (ADR-052, issue #1): `implied_probability` resolves to the latest `raw.polymarket_snapshot`/`raw.kalshi_snapshot` row captured before each game's real start time, not the settled/current price. Honestly scoped: only games from 2026-08-02 on (whenever ADR-049's forward-capture started) have a qualifying snapshot at all; everything earlier is `NULL` until the historical `--mode backfill` connectors are owner-triggered (a separate, real API-cost decision — see ADR-052's own "Revisit if").

**Market-implied probability is now a comparison line** (ADR-053, `mlb_baseball/model/market.py`): `record()` writes `core.market`'s home-team `implied_probability` into `gold.prediction` as two more `model_version`s, `polymarket-v1`/`kalshi-v1`, alongside `log5-v1`/`elo-v1`/`gbm-v1` — retrospective by construction (market data only ever resolves for already-decided games, unlike the other three), not a live feed. Caught and fixed two real bugs running this against production before it shipped: a Polymarket moneyline/spread/first-five-innings fan-out that hit `gold.prediction`'s own PK constraint on the first run, and a `backfill_outcomes()` ordering bug that left every new market prediction's outcome NULL for a needless extra cron cycle. First real matched-sample comparison (2026-08-04, 21 games — small, an early data point, not a conclusion): `gbm-v1` narrowly leads on log-loss (0.6772), both markets tie `gbm-v1` on raw accuracy (13/21) while `log5-v1`/`elo-v1` lag on this specific small sample. Full numbers and caveats in ADR-053. Next: revisit once market coverage grows past a few dozen games; a genuinely live version (market odds next to model predictions *before* the game, matching what the eventual site needs) requires extending `core.market`'s own matching to still-upcoming games first — real, separate follow-up work.

**Run-total (over/under) prediction is now a second, genuinely different target** (ADR-056, `mlb_baseball/model/total.py`, `gold.total_prediction`): expected *combined* runs scored, not win/loss — an `XGBRegressor` predicting `core.game.home_score + away_score` directly, checked against production first and found that `core.market` has zero usable total-runs data today (Polymarket's totals markets resolve "Over"/"Under" outcomes, which `conform.py`'s team-name-matching logic silently drops), so this is regression against the raw target rather than classification against a specific betting line — the safer, immediately-buildable v1. Feature set built from real correlation against total runs (park factor, team wOBA/wRC+, starter/bullpen FIP/K%/BB%/HR%), deliberately excluding the win/loss-oriented columns `gbm-v1` uses (near-zero correlation with a total-runs target — a team can be "strong" via either run-suppressing pitching or run-inflating hitting, so win/loss rating carries no consistent sign here) and the still-unpopulated weather columns (a real, confirmed gap: 0 of 216,729+ rows). Naive baseline is "the park's trailing average total," built by reusing `park_factor` rather than a second parallel query. Real verification against production (read-only, same 2023/2024-2025 train/validation split as `gbm-v1`): `total-v1` RMSE 4.4139 vs. the baseline's 4.4562 (MAE 3.4701 vs. 3.5236) — beats the baseline, a real but modest improvement consistent with run totals being a genuinely noisy target. `gold.total_prediction` is a new table, not a reuse of `gold.prediction`'s win/loss-probability shape — full reasoning and the real numbers in ADR-056. Not yet wired into `mlb_baseball/model/__init__.py`'s `run()`/`train()`/`health_check()` — a follow-up merge step, spelled out in ADR-056's own "Not wired" note.

**Gold-layer reporting surface built ahead of Phase 3, in service of it** (ADR-057, `mlb_baseball/report.py`): `gold.player_season`, `gold.team_season`, `gold.division_standing` — one flat, materialized table per entity/grain (batting/pitching season lines, team season stats + advanced metrics, division standings), sourced from already-conformed `core` plus already-computed `model/*.py` season aggregates. Not itself modeling or website work — a data-layer prerequisite so the eventual Astro site can query one table per page instead of assembling from a dozen raw/core tables at request time. **`mlb report` doesn't exist as a CLI command yet, and `mlb doctor` doesn't check it** — see ADR-057's own "Not wired in yet" for the exact `cli.py`/`doctor.py` changes still needed.

**Stacking meta-learner built, but not (yet) beating the baselines it stacks** (ADR-058, `mlb_baseball/model/stack.py`, `stack-v1`): a logistic regression over `log5-v1`/`elo-v1`/`gbm-v1`'s own latest `gold.prediction` probabilities (plus `polymarket-v1`/`kalshi-v1`'s as optional, missing-indicator-backed inputs), closing `docs/RESEARCH.md`'s "Model stacking / ensembling" section's own "(b) a legitimate later refinement" item. Scoped assuming "hundreds" of real decided games would have a prediction from all three base models; verified directly against production instead of assumed — only 47 do, because `gbm-v1` has so far only ever predicted a narrow, recent window of games (173 distinct games total, ever). That small-n reality is exactly why logistic regression was chosen over `gbm.py`'s own XGBoost precedent — a boosted-tree meta-learner over 3-7 features at ~37 training rows would have real overfitting risk a linear combiner doesn't. **Honest result on real held-out production data: the stack did not beat `gbm-v1` (0.7174 vs `gbm-v1`'s 0.6932 log-loss, n=10 held-out games) — `train()`'s own "only save if it beats every baseline" guard correctly declined to save it, so no `stack-v1` predictions are served yet.** A plausible, understood outcome (`gbm-v1` already ingests most of the same underlying signal directly as features, and 37 training rows is thin for fitting 7 coefficients), not a bug — full numbers and reasoning in ADR-058. Next: revisit once `gbm-v1`'s own decided-game count grows well past 173, the regime this module was originally scoped for.

## Phase 3 — Astro website (oddstrader-style)

Not planned yet. The gold-layer reporting surface above (`gold.player_season`/`team_season`/`division_standing`) is a real, deliberate head start on this phase's eventual data needs, built once the underlying stats were already sitting scattered across `core`/`model` with no single queryable home — see ADR-057. No UI, API, or Astro code exists yet.
